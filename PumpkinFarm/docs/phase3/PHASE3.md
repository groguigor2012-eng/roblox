# Phase 3/5: Enemy AI and wave spawning

This continues from Phases 1 and 2. Nothing was replaced with a simpler version, and no API was
renamed. The only exception is an internal Mole state, renamed `Combat` → `Interrupted` to match
the brief.

**Source:** [PHASE3_SOURCE.md](PHASE3_SOURCE.md) holds the complete, current Luau source of the
30 files in this phase, under their exact Studio paths. It is generated by
`tools/bundle_phases.py`.

> **Status.** The enemy layer was already in the repository. Checking it against this brief led to
> these changes:
> 1. **Mole:** the state machine now has the brief's exact 10 states, adding
>    `SearchingSurfaceRoute` and `Interrupted`. It re-validates the exit before surfacing and digs
>    a detour tunnel when the exit is blocked.
> 2. **Scarecrow:** wall bypass. It now vaults fences and rocks, not just barricades.
> 3. **Witch:** stays behind the frontline.
> 4. **Boss:** barricades can never soak boss damage; every boss hit crushes them. The aura's speed
>    and attack-speed buffs are now read from the boss's own config (before, those values were
>    unused).
> 5. **Waves:** a threat budget.
> 6. **AI updates:** think rates that change per state.
> 7. **Zombie Farmer:** barricades are now a configurable target.
>
> Three new end-to-end scenarios test all of this ([§10](#10-testing)).

## 1. EnemyBase architecture

`Server.AI.EnemyBase` is the base class. Each enemy type is a subclass (`setmetatable({},
{ __index = EnemyBase })`) named by `EnemyConfig.<Id>.Class`. `EnemyService` creates them:

```
EnemyService:SpawnEnemy(match, enemyId, cframe, options)
  → DifficultyService:GetEnemyStats(enemyId, context)      -- wave, players, Continue level
  → require(Server.AI[definition.Class]).new(match, definition, stats, cframe, options)
  → enemy:Spawn()   -- model (ModelFactory or an asset override), attributes, collision group,
                    -- server network ownership, OnSpawned()
  → AIScheduler:Add(enemy)
```

| Lifecycle step | EnemyBase method | Subclass hook |
|---|---|---|
| Initialization | `new`, `Spawn` | `OnSpawned` (navigator, mover, state machine) |
| Configuration | `Definition` (EnemyConfig), `Stats` (scaled) | — |
| Target acquisition | `RefreshTarget(now, options)`, throttled to every 1.5 s or when the target becomes invalid; uses `TargetSelector` | per-subclass `Kinds` filters |
| State updates | `Update(now, dt)` from the AIScheduler: validity, kill plane, then `Think` | `Think`, often a `StateMachine` |
| Movement | `Navigator` (ground), `MoverRig` (air / underground), ballistic leaps | — |
| Attacking | `CanAttack`, `AttackTarget` (reach includes the target and body radii), `GetDamageAgainst` (crop, structure or player damage) | the boss overrides `AttackTarget` |
| Taking damage | `TakeDamage` (underground rule, contributions for assists) → `OnDamaged` | the Mole is interrupted when hit |
| Death | `Die(killer)`: marks dead, `OnDeath`, rewards through `RewardService` (killer + assists), death effect, corpse cleanup | `OnDeath` (boss rewards, Mole surfaces) |
| Cleanup | `Despawn(reason)` / `Destroy()`: scheduler removal, Janitor (model, connections, movers, machines), `EnemyRemoved` signal | `OnDestroy` |

**Damage interface.** Every damageable object (`PlayerSession`, `Crop`, `Defense`, `FarmCore`,
enemies) implements `Kind`, `IsAlive()`, `GetPosition()` and `TakeDamage(amount, source)`. Enemies
don't care what they hit.

## 2. Zombie Farmer

`AI/ZombieFarmer` is the frontline grunt. Each think:
1. refresh the target
2. attack it if within reach
3. if a defense blocks the path (`Navigator:GetBlockingDefense`), attack the defense
4. otherwise path to `TargetSelector.GetApproachPoint(target)`

The target priority comes entirely from config:

```lua
TargetPriority = { Crop = 3, Core = 1, Player = 2.5, Sentry = 1.2, Barricade = 0.6 },
DetectionRange = 20,   -- players only count inside this radius (aggro)
LeashRange = 34,       -- and are dropped beyond this one
```

Changing the numbers changes the behaviour. For example, `Barricade = 4` makes farmers hunt
barricades first, and removing `Player` makes them ignore players. Barricade `PathfindingModifier`s
cost 25, so farmers prefer an open gate and only fight through when every gate is sealed. The
Witch's minions (`ZombieFarmerMini`) use the same class with their own config.

## 3. Zombie Mole

### State machine (10 states)

```
Idle ─► SelectingTarget ─► EnteringUnderground ─► UndergroundTraversal ─► SearchingSurfaceRoute ─► Resurfacing ─► AttackingCrop
              │  ▲                                     ▲      │                 │                                    │
              │  └──────────── Retargeting ◄───────────┼──────┘ (crop gone)     └─► UndergroundTraversal (detour)    │
              └──► Interrupted ◄────────────────────────────────────────────────────────────────────────────────────┘ (a player hit it)
any ─► Dying
```

| State | What happens |
|---|---|
| Idle | 0.4 s settle after spawning |
| SelectingTarget | `TargetSelector.Select(self, { Kinds = { Crop, Core } })`. If standing on bedrock, walk to the nearest soil first (`FindNearestDiggable`). If the target is within 14 studs, just walk. Otherwise `_planRoute`: pick a resurface point, then A* a tunnel. With no route, fight on the surface. |
| EnteringUnderground | body set to Ghost collision; `PlatformStand`; the MoverRig sinks it to `floor − DigDepth` over `EnterDuration`; dig effect; the body is hidden and a dirt mound is welded above it |
| UndergroundTraversal | drives the buried body waypoint by waypoint (`AlignPosition` at `floor − DigDepth`, speed-capped at `UndergroundSpeed`, slowed by status effects). If the target dies, go to **Retargeting**. If the route ends or the deadline passes, go to **SearchingSurfaceRoute**. |
| SearchingSurfaceRoute | re-validates the exit (see below). If it's valid, go to **Resurfacing**. If it's blocked, find another valid point near the target (or near itself), plan a short detour tunnel, and go back to **UndergroundTraversal** (up to `SurfaceSearchAttempts` = 3). After that, it surfaces where it is. |
| Resurfacing | vertical rise at the validated point over `ResurfaceDuration`; dig-out effect; visible again; normal collision; server network ownership |
| AttackingCrop | attacks the crop, or walks to its approach point |
| Retargeting | picks the next crop. Underground, it re-plans the tunnel from where it is; on the surface, it walks or digs again. |
| Interrupted | a player hit it on the surface: it fights that player until no hit lands for `CombatTimeout` (6 s), then retargets |
| Dying | clears the route and target, snaps a buried corpse to the surface, makes it visible, and stops the mover |

### How underground navigation works

Roblox's PathfindingService can't plan through the ground, so the Mole uses a validated
underground grid with raycast transitions:

1. **Dig grid.** `UndergroundRouter.ForArena` overlays a 4-stud grid on the arena bounds. A cell
   is diggable when a downward `Workspace:Raycast`, limited to `Map/Ground`, hits a part with
   `Diggable = true` and no `NoDig`. Rocks, the Great Pumpkin's foundation and the chest pad are
   bedrock. Each cell is probed lazily and cached for the match, so each one is raycast at most
   once.
2. **Barricade bypass.** Fences and defenses are not in `Ground`, so they don't block the grid.
   Tunnels pass under the outer defenses by design.
3. **Route.** 8-way A* with an octile heuristic. Corners can't be cut between two bedrock cells.
   The search is bounded by `MaxRouteExpansions` (6000). The result is string-pulled with a
   tunnel-width check, so the Mole moves in long straight tunnels.
4. **Exit point.** `FindResurfacePoint` tries rings 3.5 / 5.5 / 7.5 studs around the crop. A point
   is valid when the grid says diggable, and a body-sized `GetPartBoundsInBox` (4×5×4 studs,
   starting just above the plot surface) finds no defense, prop, rock, the Great Pumpkin or the
   chest.
5. **Controlled traversal.** The buried root is moved by a `MoverRig` (`AlignPosition` +
   `AlignOrientation`) with a max speed. Travel takes real time and can be interrupted, and the
   Mole is never teleported. The simulation checks this: the largest per-frame step underground
   stays below 3 studs.
6. **Surface checks.** On arrival the exit is checked again, because a defense may have been
   built there meanwhile. A blocked exit means a detour, never surfacing inside an object.
7. **Buried rules.** Melee and sentries can't hit it. Area magic (`CanHitUnderground`) deals
   ×0.5 damage. Dying underground brings the corpse up.
8. **Cleanup.** The Janitor owns the mound, mover, navigator and state machine.

Think rate per state (`StateUpdateIntervals`): traversal 0.1 s, attack 0.15 s, idle 0.3 s,
dying 1 s.

## 4. Blighted Scarecrow and the stun system

`Chasing → LeapWindup → Leaping → Landing → Chasing` (+ `Dying`).

| Behaviour | Implementation |
|---|---|
| Target | players first (`Player = 5`, detection 80, leash 120) |
| Obstacle detection | body-height rays toward the target (`LeapTriggerRange` 16): against defenses, and against props and ground obstacles (fences, rocks) for anything taller than a step; also the navigator's blocking defense |
| Leap trigger | an obstacle ahead, or the target 10–38 studs away, and `LeapCooldown` (6 s, starting on landing) has expired |
| Landing validation | downward raycast against the arena ground: must hit floor level (not outside the map, not on a rock). If the first spot fails, it tries 6 studs further. |
| Wall bypass | during the leap the body is Ghost-collided and follows a ballistic `AssemblyLinearVelocity` (`MathUtil.BallisticVelocity`). On exit it snaps to the validated landing spot, so it's never embedded in the wall. |
| Telegraph | `LeapWindup` 0.45 s plays a warning circle at the landing spot |
| Landing | shockwave: damage and a 2 s stun to players within `LandingRadius`; structure damage to defenses |

### Stun / status system

`StunService` is built on `StatusEffectService`'s `Stunned` effect:
- **Server-authoritative.** The server sets `WalkSpeed` and `JumpHeight` to 0. If a modified
  client moves anyway, it is snapped back to the stun anchor (`StunMaxDisplacement`).
- **No infinite extension.** `Stacking = "Ignore"`, so a second stun while stunned is refused.
  After a stun there is a 1.5 s **immunity** window.
- **Self-cleaning.** A single sweep loop expires effects and calls `OnStatusEffectsChanged`, which
  restores speed and jump from the class stats.
- **Death** calls `ClearTarget`: effects and immunity are dropped and movement is restored on
  respawn.
- **Leaving:** the next sweep drops effects for a target that is no longer alive, and the stun
  anchor is dropped when the root is gone.

Other effects use the same rules: `Slowed`, `Hexed`, `Chilled`, `BossAura` and `SpawnProtection`.
Each can be overridden per application (see §7).

## 5. Plague Crows

`Retargeting → Cruising → Diving → Stealing → Escaping` (+ `Dying`). The crow is moved by a
**MoverRig**, not ground pathfinding:

| Behaviour | Implementation |
|---|---|
| Flight | `AlignPosition` / `AlignOrientation` toward steering goals; no Humanoid |
| Terrain avoidance | ground raycast keeps `CruiseAltitude` (26) above whatever is below; a forward raycast climbs over obstacles |
| Ignores barricades | Ghost collision group; air movement never paths |
| Crop priority | `TargetPriority = { Crop = 5, Core = 1 }` |
| Stealing | dives to hover above the crop, then `StealCrop` after `StealDuration`. Anchored crops (Void Pumpkin) can't be stolen, so it pecks them. The stolen crop's model is carried visibly. |
| Moving between crops | if its crop is harvested, eaten or stolen first, or is too heavy and pecked to death, it goes back to Retargeting and the next crop |
| Escape | flies to the nearest arena edge and despawns with the loot |
| Attackable | creature hit tests (distance to the projectile or swing path) because its Ghost parts ignore raycasts; staffs, the scythe and anti-air sentries (Pumpkin Sentry, `CanTargetAir`) hit it |
| Death | if it's carrying a ripe crop, `RewardService:OnStolenCropRecovered` returns it to the chest |

## 6. The Witch

| Behaviour | Implementation |
|---|---|
| Backline spawning | Witches enter only after the first 30 % of the wave (`FrontlineLead`) |
| Behind the frontline | the inner edge of its 24–44 stud band is pushed out to the closest allied ground enemy's distance to the player + `FrontlineBuffer` (6), so the horde stays between the witch and the defenders |
| Repositioning | retreats when too close, advances when too far, separates from other witches (`SeparationRadius`), stays inside the arena bounds |
| Player targeting | nearest living player |
| Line of sight | `Workspace:Raycast` against the arena map (fences, rocks, props) before every throw |
| Slowing potion | `ProjectileSystem` ballistic projectile with gravity, aimed at the player's predicted position. Collision is resolved on the server: each step raycasts the segment it travelled against the world and tests players by distance to that segment. The splash (9 studs) damages and applies `Slowed`. |
| Minions | `ZombieFarmerMini` × 2 every `SummonCooldown` (12 s), never more than `MaxMinions` (4) alive per witch. Minions count toward Zombies Left. |

## 8. Wave spawner

| Requirement | Implementation |
|---|---|
| Difficulty scaling | `DifficultyConfig.Curves`: **Health ×1.2/wave** (soft cap at wave 15, then ×1.05, max ×40). **Speed ×1.2/wave, damped** (exponent 0.15, max ×1.6, so enemies stay fair). Damage ×1.2 damped. Per-enemy `Scaling` weights. |
| Continue multiplier | ×1.5 per level, weighted per stat (health 1, speed 0.3, damage 0.5, density 0.6, spawn pressure 0.5, boss health 1); more specialists |
| Enemy count | `(6 + 2.5·(w−1)) · 1.035^(w−1)`, +50 % per extra player, capped at 140 |
| **Threat budget** | `budget = slots × min(2.6, 1.25 + 0.06·(w−1)) + 0.2·Continue`. Costs: grunt 1, crow 1.5, mole 2, scarecrow 2.5, witch 4. A specialist is only picked while the budget can pay for it **and** a grunt for every remaining slot. The boss is outside the budget. |
| Evolving composition | unlock waves: moles 3, crows 4, scarecrows 6, witches 8. The specialist share grows from 10 % to 55 %. Each archetype is capped by `MaxShare` / `MaxPerWave`. Early waves are farmers; mid waves add moles and scarecrows; later waves add crows, witches and mixed groups. |
| Boss logic | every 10th wave, boss first |
| Spawn points | 8 grave spawn points on a 160-stud ring, random offset; flyers 30 studs up; the boss at the point farthest from the players |
| Caps and concurrency | at most **45 alive per match** (the spawner waits); bursts of 1–4; at most 4 matches per server |
| Pacing | interval `1.6 − 0.05·(w−1)` s (minimum 0.35), shortened by Continue pressure |
| Zombies Left | `EnemiesRemaining` = alive + still to spawn (minions included), published when it changes |
| Wave completion | `IsWaveCleared` = spawner finished **and** no enemy alive. The state machine moves to WaveComplete exactly once. |
| Intermission | after WaveComplete: shop restock, 25 s (Extraction every 5th wave) |

`WaveComposer.Compose` is a pure, deterministic function of `(wave, context, seeded Random)` and is
unit-tested.

## 9. Objective system and performance

**`TargetSelector`** is the shared objective system. Its candidates come from the match registries:
- **Player**: living sessions inside `DetectionRange`
- **Crop**: `CropService`
- **Barricade** and **Sentry**: `DefenseService`
- **Farm objective**: `match.Core`

```
score = TargetPriority[kind] × (1 + decoy bonus) / (1 + distance / 40)
```

- A `Kinds` filter restricts the candidate types (the Mole only considers crops and the core).
- 30 % hysteresis keeps the current target unless a new one is clearly better.
- `IsValid` enforces the leash and match membership.
- `GetApproachPoint` returns a walkable point just outside solid targets.

| Technique | Where |
|---|---|
| One scheduler, per-agent think rates | `AIScheduler`: one Heartbeat for all enemies, round-robin, at most 40 updates per frame (large waves think slightly slower instead of spiking), random phase per agent |
| State-specific update rates | `EnemyBase:BindStateUpdateIntervals(machine)` + `StateUpdateIntervals` in config (Mole: 0.1–1 s per state) |
| Throttled target acquisition | `RefreshTarget`: every 1.5 s, or immediately when the target becomes invalid |
| Cached targets | `enemy.Target` with hysteresis; registries instead of workspace scans |
| Path recalculation intervals | Navigator: walks directly when close with line of sight; otherwise re-paths only when the goal moves more than 8 studs, it's stuck, or the path runs out (at most once per 1.5 s). `PathQueue` allows at most 6 concurrent `ComputeAsync`, and requests from dead agents are skipped. |
| Raycast caches | Mole dig grid (each cell probed once per match) |
| Cancellation | every enemy owns a Janitor (movers, navigators, machines, connections). `Despawn` removes it from the scheduler at once. Path requests for dead agents are dropped. |
| Cleanup | `CleanupService` sweeps orphan models every 30 s; corpses are removed after the death effect |

## 10. Testing

### Automated

`tests/run.sh` runs 226 specs, including `wave_spec`:
- plans never overspend the threat budget (waves 1–60, Continue levels 0–3, 1 and 4 players)
- the budget binds and grows with the wave and with Continue
- composition evolves (early, mid, late), with the boss every 10 waves
- plus the existing unlock, cap and determinism tests

`router_spec` covers A*, bedrock, the diagonal squeeze, bounds and resurface points.

Simulation scenarios run the real server:

| Scenario | Proves |
|---|---|
| **zombie mole** | visits Idle → SelectingTarget → EnteringUnderground → UndergroundTraversal → SearchingSurfaceRoute → Resurfacing → AttackingCrop. Starts outside the fence and surfaces inside it.
