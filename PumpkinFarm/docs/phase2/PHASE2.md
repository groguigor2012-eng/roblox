## 1. Match lifecycle

**Lobby → Match.**
1. A player queues through the Farm Portal prompt or the Play button (`RequestJoinQueue`).
2. `LobbyService` only accepts players whose profile has loaded.
3. The first player in the queue starts an 8 s countdown (`QueueEndsAt` and `QueueSize` attributes).
4. The match launches when the countdown ends or the queue reaches 4 players.

**`MatchService:CreateMatch(sessions)`:**
1. Allocates an arena slot. There are 4 per server; if none is free, the queue waits with
   `QueueFull`.
2. Builds the `Match`, which builds the arena through `MapBuilder.BuildArena`: ground, fence, gates,
   6 plots × 6 slots, core, chest pad, door position and spawns.
3. Calls `InitMatch` on each per-match service in this order:
   `CropService → SeedShopService → HarvestChestService → BarricadeService → SentryService →
   DefenseService → EnemyService → WaveService → EscapeService`
4. Sets each session to `InMatch` and starts the state machine.

**Farm assignment** happens in `CropService:InitMatch`. Players, sorted by UserId, each take
`MatchConfig.Farm.PlotsPerPlayer` plots in `PlotOrder`. The remaining plots are shared (see §3).

| State | Enter | Exit |
|---|---|---|
| Waiting | each player is spawned at an arena spawn | everyone alive, or 15 s |
| Starting | starting Match Coins (150 + Deep Pockets), soft-lock seed grant, first restock, class weapon | 5 s |
| Intermission | shop restocked (except the first time) and opened | 40 s first, 25 s later |
| PreparingWave | `Wave += 1`, wave plan composed, banner; shop closed | 4 s |
| WaveActive / BossWave | spawner runs | spawner finished and no enemy alive |
| WaveComplete | wave coins `40 + 8·wave`, downed players revived, shop open | 4 s |
| Extraction (every 5th wave) | Escape Door opens, 30 s decision | EscapeService resolves: Continue or End |
| ContinuePreparation | `ContinueLevel += 1`, difficulty ×1.5, heal players, repair defenses 35 %, core +25 %, crops healed, restock, shop open | 30 s, then PreparingWave |
| MatchEnding | stop the wave, forfeit the chest if lost, commit stats, results card | 8 s |
| Cleanup | remaining players returned to the lobby; every per-match service's `CleanupMatch` in reverse order; the match Janitor destroys the folder | — |

Losing happens when the Great Pumpkin is destroyed, or when every player is down during a wave
(`Wiped`). If everyone leaves, the match ends as `Abandoned`. Timers are replicated as
`PhaseEndsAt` (server time), so every client counts down to the same moment.

## 2. Randomized Seed Shop

| Piece | File | Role |
|---|---|---|
| Seed rules | `Shared.Config.SeedConfig` | per seed: `Weight` (rarity weight), `MinWave`, `Quantity {min,max}` (scaled by player count), `PriceVariance {min,max}`, `PerPlayerLimit`, `AlwaysStocked` |
| Crop data | `Shared.Config.CropConfig` | base `SeedPrice`, `Rarity`, growth, health, yield, value |
| Rarity | `Shared.Data.Rarity` | tiers and colours |
| Stock model | `Server.Classes.SeedShop` | `GenerateStock(rng, context)` is pure and deterministic; `Restock` bumps `Version`; `CheckPurchase` + `CommitPurchase` |
| Server | `Server.Services.SeedShopService` | owns each match's shop, restocks at every Intermission and ContinuePreparation from the match's seeded `Random`, opens and closes with the state (`MatchConfig.SeedShopOpenStates`), handles `RequestBuySeed`, broadcasts `ShopUpdated` |
| Inventory | `Server.Services.SeedService` | the persistent seed pouch `profile.Seeds[seedId] = count`: `GetSeedCount`, `AddSeeds`, `ConsumeSeed`, soft-lock grant |
| Client | `SeedShopController` (`ShopUI`) | shop cards (icon, rarity, price, stock left, your limit, Buy) and the seed pouch bar that selects the seed to plant |

**The stock is owned by the server.** Clients only see a snapshot of it.

**Purchase pipeline** (`RequestBuySeed(seedId, stockVersion)`):
1. Rate limit: 6 burst, 3/s.
2. Schema: an id string matching `^[%w_]+$` and an integer version. Anything else returns
   `InvalidPayload`.
3. In a match, with the profile loaded, and the shop open in this state. Otherwise
   `NotInMatch` / `DataNotLoaded` / `InvalidState`.
4. `CheckPurchase`:
   - the version matches (`StockChanged` if a restock happened in between)
   - the seed is in stock (`OutOfStock`)
   - the per-player limit isn't reached (`PurchaseLimit`)
5. **One profile mutation**: check Candies, deduct the price and add the seed together
   (`InsufficientFunds`, or a rollback on error).
6. `CommitPurchase` decrements the stock, then `ShopUpdated` goes to the whole match.

Nothing between steps 4 and 6 yields, so two players racing for the last seed can never both win.
`transactions_spec` and the `farm rules` simulation both test this. Repeating a request is
harmless: each one is a separate purchase that must pass every check again.

## 3. Farm plots

- **Registration.** `MapBuilder` builds 6 plots in a ring around the Great Pumpkin, each with 3×2
  slots (`MatchConfig.Farm`).
  - Plot parts: `Map.Ground.Plot<n>`, attributes `PlotId` and `Diggable`.
  - Slot parts: `Map.Props.Slot<n>`, attributes `PlotId` and `SlotIndex`.
  - The layout (`Arena.Plots[plotId].Slots[i].Position`) is the server's source of truth.
- **Planting zones.** Planting is slot-based: the client sends `(plotId, slotIndex, seedId)`, never
  a position. A position outside the farm or inside an object therefore can't be expressed.
- **Ownership.** Each player owns `PlotsPerPlayer` (1) plot. The other plots are shared.
  - Owners are replicated as `PlotOwnerId` (UserId, 0 = shared) and `PlotOwnerName` on the plot
    and slot parts.
  - Only the owner can plant on an owned plot (`NotYourPlot`). Anyone can harvest anywhere, because
    the chest belongs to the team.
  - When a player leaves the match (escape, death-loss or disconnect), `MatchService` calls
    `CropService:ReleasePlots` and their plot becomes shared.
- **Server checks when planting**, in order:
  1. in a match, alive, and the match isn't ending
  2. plot and slot exist in *this* match
  3. the player may plant on this plot
  4. the planting cooldown has passed (0.5 s, `Cooldown`)
  5. the slot is empty (`Occupied`)
  6. the character is within 14 studs of the slot (`OutOfRange`)
  7. no defense overlaps the slot (box query, `Blocked`)
  8. the seed is owned and consumed (`NotOwned`)

  A rejected plant never consumes a seed.

## 4. Crop system

`Server.Classes.Crop` is an OOP class, one instance per planted crop:

| Concern | Implementation |
|---|---|
| Creation | `Crop.new(match, definition, slot, plantedBy, growthMultiplier, onDepleted)` builds `Crops/Crop_<uid>` with a persistent `Anchor` part and a `Visual` child |
| Growth | `Update(dt)` is called by CropService's single loop (every `CropConfig.TickInterval`). Growth goes from 0 to 1 over `GrowthDuration`, faster with the Green Thumb upgrade. |
| Stages | 4 stages (seedling → sprout → growing → ripe). The `Visual` model is rebuilt by `ModelFactory` at each stage, scaled per stage. The game logic reads only `Growth`, `Stage` and `Ripe` on the server; visuals never drive logic. |
| Health | `Health` / `MaxHealth` are server-owned and replicated as attributes |
| Damage | `TakeDamage(amount, source)` with per-attacker vulnerability. Specials: Thorns hits back; Regenerate heals itself. |
| Destruction | at 0 health → `onDepleted` → `CropService:DestroyCrop(crop, "Eaten")` |
| Harvest | `IsRipe()`; `CropService:Harvest` |
| Yield and value | `YieldQuantity` units × `UnitValue` Candy value (CropConfig) |
| Cleanup | `Destroy()` releases the Janitor (model, connections). CropService drops every reference. |

| Crop | Rarity | Seed | Grows | Yield × value | Special |
|---|---|---|---|---|---|
| Neon Star-Fruit | Common | 30 | 40 s | 2 × 40 | — |
| Phantom Corn | Uncommon | 55 | 55 s | 4 × 25 | Decoy: enemies prefer it |
| Ghost Pepper | Uncommon | 80 | 70 s | 3 × 50 | Thorns: 12 damage to attackers |
| Void Pumpkin | Rare | 220 | 120 s | 1 × 600 | Anchored: crows can't steal it |
| Wraith Melon | Epic | 450 | 160 s | 1 × 1100 | Regenerate: 4 HP/s |

Phantom Corn and Wraith Melon are the original extras. The corn is a cheap decoy that protects
valuable crops; the melon is a high-risk late-game crop.

## 5. Crop damage

Enemies attack crops through the damageable-target interface: `TakeDamage`, `IsAlive`,
`GetPosition`. The server owns health. At zero, `CropService:DestroyCrop(crop, reason)`:
1. returns at once if the crop is no longer registered, so a second call is a no-op
2. removes it from `Crops[uid]` and frees its slot
3. plays an effect, and warns the team if the crop was ripe or rare
4. `crop:Destroy()` removes the model; clients see the `Crops` child disappear and clean up the
   billboard and prompt
5. fires `CropService.CropRemoved(match, crop, reason)` with reason `Eaten`, `Stolen` or
   `Harvested`

AI targets re-check `IsAlive()` before every hit, so a destroyed crop is never a target. Plague
Crows use `StealCrop`; killing the crow returns a ripe crop to the chest.

## 6. Harvest Chest

| Piece | Role |
|---|---|
| `Server.Classes.HarvestChest` | pure data ledger (no Instances). Stacks per item id (`Quantity`, `UnitValue`, `Value`). Deposits are validated (positive integer quantity, finite value). There is no withdraw API. |
| Capacity | `EconomyConfig.Chest = { MaxItems = 400, MaxStacks = 16 }`. `CanDeposit` is checked **before** the crop is removed, so a full chest returns `ChestFull` and the crop stays planted. Boss rewards are forced and always fit. |
| `HarvestChestService` | one chest per match plus its model and `ChestPrompt` (`OpensUI = "HarvestUI"`). Broadcasts `ChestUpdated` (entries, total, estimated Candies, risk bonus, capacity) and the `ChestValue` attribute on every change. |
| Duplicate harvest | `CropService:Harvest` removes the crop **before** paying, so a repeated request finds nothing (`NotFound`) |
| Payout | `floor(total × ConversionRate × (1 + 0.25 × ContinueLevel))`. Every escaping player gets the full team chest. |
| Loss | `Forfeit()`: emptied and locked |
| Cleanup | the model is destroyed and the state dropped in `CleanupMatch` |

## 7. Match Coins

`MatchCoinService` keeps each balance in server memory and mirrors it to the `MatchCoins`
attribute. `Reset` runs at match start; `Clear` runs on escape, loss or leave, so coins never reach
the profile.

| Earn | Amount |
|---|---|
| Start | 150 + 25 per Deep Pockets level |
| Kill | per-enemy `CoinReward`, +5 % per wave; assists get 40 % above 10 % damage dealt |
| Wave complete | 40 + 8 × wave |
| Boss kill | 400 |

| Spend (`DefenseConfig`) | Kind | Cost |
|---|---|---|
| Wooden / Iron Barricade | placed | 50 / 140 (upgrades 60, 110 / 150, 260) |
| Pumpkin Sentry / Hex Lantern | placed | 180 / 160 |
| Pumpkin Helmet, Swift Boots, Lucky Charm | accessory (lasts the match, one each) | 120, 100, 150 |
| Healing Tonic, Repair Kit | utility (consumed, cooldown) | 40, 90 |

Every spend goes through `CurrencyService:TrySpend(player, "MatchCoins", amount, reason)`, which is
check-and-deduct with no yield in between. If construction then fails, the coins are refunded.

## 8. Escape Door

At **Extraction**, `EscapeService:OpenDoor` creates the physical `EscapeDoor`. It has two
ProximityPrompts: **ESCAPE TO THE LOBBY** (E / X), which shows the payout, and **CONTINUE**
(F / Y), which shows the next danger level. Clients also get `ExtractionUpdated` for the EscapeUI
panel. Both paths call `EscapeService:SubmitDecision`.

**Validation:** the player is in this match, alive, and within 18 studs of the door; the door is
open; and the player hasn't decided yet (`AlreadyDone`).

**Escape flow** (`ProcessEscape`):
1. `Paid[userId] = true` is set **first**, so a duplicate can never pay twice
2. freeze the payout from the server chest
3. Candies to the profile (`CurrencyService → CandyService → DataService`)
4. statistics (`RewardService:CommitMatchStats`, escaped)
5. save
6. strip match-only state
7. return to the lobby

**Continue flow:** when everyone has decided, or the 30 s window ends:
- If anyone chose CONTINUE, the undecided players continue with them. The match enters
  **ContinuePreparation**: a 30 s countdown, difficulty ×1.5 per level, a higher risk bonus, a
  restock, and partial repairs. Then waves resume.
- If nobody chose CONTINUE, undecided players are escaped and paid, and the match ends.

**Protection against abuse:**
- one decision per player
- paid before any yield
- decisions are only accepted while the state is Extraction (`InvalidState`)
- the door is server-validated, so prompts are only a convenience
- the Match state machine refuses illegal transitions

## 10. Defense foundation

| Piece | Role |
|---|---|
| `Defense` (base class) | health, `TakeDamage`, `Repair`, upgrade levels, owner, model `Defenses/<Id>_<uid>` with attributes `DefenseUid`, `DefenseId`, `Health`, `MaxHealth`, `Level`, `MatchId`; parts in the `PF_Defenses` collision group (blocks enemies, not players); a Janitor |
| `Barricade` | a `PathfindingModifier` (`Barricade`, PassThrough) so enemies path around it or attack it |
| `Sentry` | finds a target in range and fires through `ProjectileSystem`; the head turns to aim |
| `BarricadeService`, `SentryService` | construction and per-match registries |
| `DefenseService` | purchase, placement validation, upgrades, accessories and utilities, queries for AI, destruction, `RepairAll` |

**Placement validation** (all server-side):
1. the spot is in the ring 14–95 studs from the farm centre and inside the arena
2. the buyer is within 45 studs
3. a downward raycast finds diggable floor (not a plot, rock or pad)
4. the footprint box (+0.5 clearance) overlaps nothing solid: defenses, crops, props, fences, the
   core, the chest
5. the match caps aren't exceeded (30 defenses, sentry cap)
6. the coins are spent; if construction fails, they are refunded

**Ownership** is `defense.Owner`. **Destruction** at 0 HP goes through
`DefenseService:DestroyDefense`, which unregisters it, plays the effect and destroys the model.
**Cleanup:** every defense is destroyed in `CleanupMatch`.
